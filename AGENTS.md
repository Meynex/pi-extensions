# pi-extensions guidelines

- Write idiomatic, maintainable TypeScript. Prefer small, focused helpers over clever code.
- Add comments only where they explain non-obvious behavior, edge cases, or terminal/TUI safety constraints.
- Treat model context as a shared budget: keep always-on schemas, descriptions, prompt metadata, agent instructions, and tool outputs concise and non-duplicative.
- Preserve the cacheable prompt prefix within a session. Keep system prompts, tool definitions and ordering, project instructions, and provider payload transforms deterministic; never inject timestamps, random values, counters, or other frequently changing state near the front of the prompt. Put mutable plan, goal, and runtime state in append-only messages or tool results instead of rebuilding the system prompt.
- Keep dynamic tool activation purely additive whenever possible: register tools up front, leave rarely used tools inactive, and add them without removing or reordering active tools. Deferred tools should normally omit `promptSnippet` and `promptGuidelines`, because activating that metadata rebuilds the system prompt. Treat removals, replacements, reasoning/model changes, historical message rewrites, and compaction as intentional cache resets.
- Prefer stable, append-oriented transcripts over pruning or rewriting historical tool calls. Context hooks must be deterministic and should modify old messages only when the behavior justifies losing prefix reuse. For cache-sensitive changes, compare cache-hit and re-billed-token statistics before and after, and add focused coverage for loadout and prompt stability.
- Before adding or updating a tool, inspect comparable tools in this repository and match their interaction and visual language: naming, schema metadata, collapsed and expanded rendering, semantic colors and icons, spacing, truncation, progress, success, empty, and error states. Reuse shared helpers and patterns where practical, cover the rendered states in tests, and make any intentional divergence explicit.
- Add or update tests for extension behavior changes. Keep tests slim and focused on regressions/user-visible behavior.
- Treat settled and persisted transcript rows as immutable snapshots. Never read `Date.now()`, mutable process state, or other live values from a historical component's `render()` path; capture observation data once and test that repeated renders stay byte-identical.
- Treat TUI redraws as potentially expensive and viewport-disrupting in very long sessions. Prefer width-keyed caches and change-driven invalidation; avoid autonomous/global redraws, off-screen row mutation, and full-transcript recomputation, and test idle behavior with a scrolled viewport in mind.
- Run the relevant focused tests while iterating, then run the full test suite before pushing.
- Treat documentation as part of the behavior contract. Update the relevant extension README in the same change whenever behavior, commands, schema fields, defaults, limits, configuration, platform restrictions, output, or user-facing UX changes.
- Keep exact README output examples backed by a renderer or command test. When rendered text changes, update the test and README example together; do not preserve illustrative output that the extension cannot produce.
- Keep repository documentation indexes synchronized: every extension directory must appear in the root README, every code-bearing extension README must include a Dependencies section, and the root direct-import graph must match source imports. Run `bun test documentation.test.ts` after adding, removing, renaming, or reconnecting extensions.
- Do not commit generated artifacts, dependency directories, logs, or local machine state.
- Do not use another agent harness as a substitute for describing behavior in code, docs, READMEs, commit messages, or PR bodies. Describe behavior in its own terms ("terminal bell", "focus-aware", etc.). Intentional, factual attribution of a feature's design inspiration is allowed.
- Push directly to `main`. Do not open pull requests. Commit with `git commit -S` and `git push origin main`. For noisy/unrelated changes, prefer a separate commit over bundling; squash only if a branch's history is unwieldy. Never bundle unrelated changes into the same commit.
